# 슬라이드 포트폴리오

`/portfolio`는 `next.config.ts`의 rewrite로 `index.html`을 제공한다. 사이트의 공통 헤더·푸터와 CSS를 적용하지 않고 원본 1920×1080 슬라이드 디자인을 유지한다. 서버에서 PDF를 생성하거나 개인정보를 전송하지 않는다.

- `index.html`: 21페이지의 문구, 링크, 이미지 배치. 내용을 변경할 때 이 파일을 수정한다.
- `deck.css`: 슬라이드·인쇄·전체 화면 스타일과 WOFF2 웹폰트 3종.
- `controller.js`: 페이지 이동, 전체 화면, 로컬 문구 편집, 저장.
- `assets.js`: 화면별 이미지 활성화와 PDF/HTML 저장용 리소스 포함 처리.
- `pdf.js`: 브라우저에서 이미지 기반 16:9 PDF를 생성하고 링크를 보존한다. 글자 선택·검색은 지원하지 않는다.
- `assets/`: 원본 PPT에서 추출한 이미지의 WebP/SVG와 WOFF2 폰트. 파일명은 내용 해시이며 장기 캐시를 사용한다. 교체할 때 새 파일명을 사용하고 참조도 갱신한다.

폰트는 KoPubWorld Dotum Medium·Bold와 Gmarket Sans Medium의 전체 글자를 포함한 WOFF2를 자체 제공한다. 문구별 서브셋·추가 CSS 로딩 없이 본문과 제목에 필요한 폰트를 적용하므로 편집한 글자도 같은 폰트를 사용한다. 브라우저는 사용하는 굵기의 파일을 다운로드하고 캐시한다. HTML·PDF 저장에도 해당 웹폰트를 포함한다. 이미지에는 첫 슬라이드를 제외하고 `data-src` 또는 `data-href`를 사용한다. 슬라이드를 열면 실제 주소를 설정한다.

PDF 저장은 방문하지 않은 페이지까지 모든 이미지와 폰트를 가져와 변환용 사본 안에 포함한다. 원격 자료를 받지 못하면 오류를 알리며 불완전한 파일을 다운로드하지 않는다. 편집 후 HTML 저장도 모든 자료를 포함한 오프라인 파일로 내려받는다. 편집 내용은 해당 브라우저의 localStorage에 저장되며 공개 원문을 바꾸지 않는다.

## 확인

`npm run dev` 후 `/portfolio`에서 확인한다. `npm run lint`와 `npm run build`를 실행한다. Playwright가 있는 환경에서는 다음 브라우저 검증도 사용할 수 있다. 프로젝트 런타임 의존성을 추가할 필요는 없다.

```sh
PORTFOLIO_URL=http://localhost:3000/portfolio node scripts/check-portfolio.mjs
```

별도로 설치된 Playwright는 `PLAYWRIGHT_MODULE`에 모듈 경로를, Chrome은 `CHROME_PATH`에 실행 파일 경로를 지정한다. 검증은 초기 전송량, 지연 로딩, 전체 화면, 문구 보존, 직접 PDF 다운로드, 오프라인 HTML 저장을 확인하고 임시 폴더에 PDF와 화면 캡처를 남긴다. PDF의 페이지 수·문구 배치·이미지와 링크는 결과 파일로 확인한다.

원본 보관본은 Lifebase의 `2026-09-17-portfolio.html`이며 이 디렉터리가 웹 공개용 소스다. 2026-09-17 콘텐츠 개정에서는 사이트의 `Profile.tsx`, `lifebase.mdx`, `day-planner-enhanced.mdx`와 Lifebase 커리어 기록을 근거로 경력·교육·자격을 갱신했다. 원본 보관본은 유지한다.

프로젝트는 업무 프로젝트와 개인·팀 프로젝트로 구분한다. 각 묶음 앞에 세로선과 중앙 Projects 제목을 둔 구분장을 배치하고, 다음에 이어질 분류를 진하게 표시한다. Upstage 업무는 `IBK 생성형 AI 시스템 구축`과 `EWS · Enterprise AI Workspace`로 표기한다. 회사와 개인 기여를 구분하고, 최종 발표자료의 흐름을 재구성한 구성도와 평가 조건을 붙인 수치를 사용한다. IBK는 Function Call과 Chunk Validator 두 장으로 나눈다. 두 장의 프로젝트 제목·소개·참여 기간·역할은 동일하게 유지하고, 본문의 소제목·기여·다이어그램·결과만 바꾼다. 기존 프로젝트의 좌측 설명·우측 시각 자료 배치를 사용하며 별도 탭은 추가하지 않는다. Chunk Validator의 5건 검증 결과는 작은 보조 근거로 표시한다. Function Calling은 2025-07-21 Solar Pro 2의 동일 850문항 auto/required 비교를 사용한다(2.03183s → 0.40112s, 768/850 → 788/850). 회고 문서에서도 90.35% → 92.71%를 확인했으며, 최종 발표의 87.06%와는 기준이 불명확해 섞지 않는다. Chunk Validator는 2025-08-18 청크 혼입 유형 5건의 표적 평가 결과(정답 2·오답 2·오인용 1 → 정답 5)를 사용하며 전체 RAG 정확도로 일반화하지 않는다. 팀 공동 개선으로 표기하고 본인의 사례 분석·프롬프트 개선·검증 참여를 구분한다. EWS도 공통 프로젝트 정보 아래 Agent Layer와 Data Ingestion 순서의 두 장으로 구성한다. Data Ingestion은 비동기 접수·상태 조회와 파싱·청킹·임베딩·적재 흐름, Agent Layer는 병렬 분류·대화/RAG 분기·도구 호출 반복·SSE 전달을 보여준다. Agent Layer는 보존된 MainChatGraph와 스트리밍 구현을 확인해 작성했으며 장기기억·영속 메모리 또는 측정되지 않은 성능 개선을 주장하지 않는다. EWS 수치는 2025-10-15 단일 1,275페이지 PDF 처리 검증이며 속도 개선율이 아니다. IBK·EWS 구성도의 편집 원본과 SVG는 `docs/portfolio-diagrams/`에 보관한다. EWS는 사용자가 작성한 최종 인턴 발표자료 26·29장의 구조와 구현 코드를 바탕으로 포트폴리오용 다이어그램을 다시 그렸으며, 비율을 유지하고 클릭하면 크게 열린다. Data Governance placeholder와 TOBE Chunk Validator는 제외하고 구현된 흐름을 표현한다. 메모리는 프로세스 내 상태다. 현재 회사 사례와 수치는 사용자 요청에 따른 로컬 검토 초안이며, 회사의 대외 공유 승인이 확인된 상태는 아니다. 내부 원본 화면·고객 문서·API 주소·프롬프트는 포함하지 않는다. Lifebase는 개요·하네스 아키텍처·제품 구성·업데이트 설계 네 장으로 구성한다.

중간 구분장은 `data-outline-skip`으로 목차의 중복 항목을 생략한다. 목차는 `data-outline-root`가 상위 섹션을, `data-section`이 소속을, `data-group`이 프로젝트 분류를 지정한다. HTML 저장 후에도 기존 목차 항목을 비우고 재구성해 중복을 방지한다.

슬라이드 문구의 순서가 바뀌면 인덱스 기반 편집 내용이 다른 문구에 적용되지 않도록 `controller.js`의 `storageKey` 버전을 올린다. 이전 키의 데이터는 삭제하지 않는다. 기존 사이트 내비게이션 변경이나 배포는 별도 작업이다.

사용자가 편집한 `2026-09-17-portfolio-edited (4).html`의 문구와 검토 메모를 반영했다. 코디세이·PCCP는 삭제했으며, Day Planner Enhanced는 후속 요청에 따라 More에서도 제외했다. EWS는 기존 좌우 배치를 유지하면서 왼쪽 설명 영역을 860px로 넓히고 프로젝트명과 소개를 각각 한 줄로 배치한다. Lifebase 시작 시점은 사용자가 지정한 2026.03.으로 표시하며 제품 출시일과 구분한다. 추가 스터디는 구체적인 항목이 정해지면 반영한다.

Lifebase 제목은 다른 프로젝트와 동일하게 로고 없이 표시한다. 소개 페이지의 노트 연결 그래프는 배포 사이트 `site/src/data/graph.json`과 `Graph.astro`의 좌표·반경·연결·색상을 그대로 SVG로 옮겼다. 원본 데이터는 노트 이름·경로·본문을 제외한 익명화 스냅샷이며 그래프를 클릭하면 확대해서 볼 수 있다. 웹사이트·CLI 화면은 제품 구성 페이지의 왼쪽 설명 아래로 옮겼고 기존 전체 구성도는 오른쪽에 유지한다.

Lifebase 소개 페이지의 제목·부제·본문은 프로젝트 공통 글자 크기를 사용한다. `lifebase-overview` 스타일은 설명 영역과 오른쪽 그래프의 배치만 조정한다. 나머지 Lifebase 페이지의 본문·설계도 배치는 유지한다.

소개 페이지의 제목 아래 GitHub·블로그 링크를 둔다. 경력은 3페이지에 독립 배치하고 Upstage의 직무·재직 기간과 IBK·EWS의 담당 업무를 구분한다. 4페이지는 교육·수상·자격·시험을 각각 한 열로 구성하며 ETC 항목은 생략한다.

2026-09-17 화면 캡처 갱신: 소개 페이지의 홈페이지 상단(`ce80d872bb0776ff.webp`), 블로그(`7a7cfb81dfa638b0.webp`), GitHub 기여 그래프(`af7f006a0f50137d.webp`)와 More의 홈페이지 전체(`7a9d9f713a88b11d.webp`)·프로젝트 목록(`30610c385afdf4ba.webp`)을 당시 운영 중인 `jagaldol.com`, `blog.jagaldol.com`, `github.com/jagaldol`에서 다시 캡처했다. 원본 비율을 유지하고 WebP로 저장하며, 기존 캡처는 이전 저장본의 참조를 위해 남겨둔다.

문구 편집과 HTML 저장은 `localhost`, `127.0.0.1`, `[::1]` 및 내려받은 `file:` 문서에서만 활성화한다. 배포 주소에서는 편집 버튼·E 단축키·저장 문구 복원을 사용하지 않으며, 페이지 탐색과 PDF 저장은 그대로 제공한다.

PDF와 HTML 다운로드 파일명의 날짜는 `index.html`의 `portfolio-modified` 메타데이터를 사용한다. `document.lastModified`나 배포 시각은 사용하지 않는다. 포트폴리오 HTML·CSS와 참조 이미지·폰트의 내용 해시가 같으면 날짜도 유지되며, 저장한 독립 HTML에도 메타데이터가 포함된다.

`npm run dev`와 `npm run build` 전에 버전 스크립트를 실행한다. 로컬에서는 관련 파일의 마지막 Git 커밋 시각과 미커밋 파일의 수정 시각을 기준으로 한국 시간 날짜를 기록한다. 실행 중인 개발 서버에서 수정했다면 커밋 전에 `npm run portfolio:version`을 실행하고 변경된 `index.html`도 함께 커밋한다. Vercel/CI에서는 저장된 해시만 검증하며 날짜를 생성하지 않는다. 내용과 메타데이터가 다르면 로컬 갱신을 요청하고 빌드를 중단한다. 검증: `node scripts/check-portfolio-version.mjs`.
